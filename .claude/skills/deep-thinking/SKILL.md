# Deep Thinking 워크플로우

구현 전에 숨겨진 복잡성을 발굴하고, 기술 결정을 문서화하는 워크플로우 가이드. 핵심 원칙: 사고의 깊이가 기능적 완성도보다 중요하다.

이 스킬은 오케스트레이터가 아니다. 각 단계에서 어떤 에이전트를 사용하면 좋은지 안내하고, 필요한 단계만 선택해서 실행한다.

## 워크플로우 개요

```
1. 요구사항 도출    ─── req-analyzer (선택)
2. 약점 발굴       ─── design-challenger
3. 설계 보완       ─── 사용자 판단
4. 결정 문서화     ─── decision-documenter
5. 구현 진행
```

모든 단계를 반드시 거칠 필요 없다. 이미 요구사항이 명확하면 1단계를 건너뛰고, 설계에 자신 있으면 바로 4단계로 갈 수 있다.

## 단계별 가이드

### 1단계: 요구사항 도출 (선택)

요구사항이 모호하면 `req-analyzer`를 먼저 실행한다.

이 단계의 목적: "명시되지 않은 결정"을 찾아서 명시적으로 만드는 것. 예를 들어 요구사항에 동시성 전략, 성능 기준, 인증 모델이 빠져있다면 — 이런 누락을 발견하고 채우는 단계다.

**언제 건너뛰는가**: 요구사항 문서가 이미 있고, 주요 결정이 명시되어 있을 때.

### 2단계: 약점 발굴 (핵심)

`design-challenger`를 실행한다. 이 단계가 전체 워크플로우의 핵심이다.

대부분의 설계 결함은 happy path에서 드러나지 않는다. "공유 자원에 락을 걸면 끝"이라고 생각하지만, 같은 사용자가 동시에 두 요청을 보내면 사용자별 제약조건이 깨진다 — 이런 시나리오를 찾는 단계다.

design-challenger에게 전달할 것:
- 요구사항 문서 (있으면)
- 설계 초안 또는 기술 선택 사항
- 코드 (구현이 있는 경우)

design-challenger가 반환하는 것:
- 심각도별 약점 목록
- 각 약점의 구체적 재현 시나리오
- 해결 방향 제안

### 3단계: 설계 보완

design-challenger의 결과를 보고 설계를 보완한다. 이 단계는 에이전트가 아니라 사용자가 주도한다.

판단 기준:
- **Critical 약점**: 반드시 보완한다. 데이터 정합성이나 손실 문제는 "나중에 고치자"가 통하지 않는다.
- **Warning 약점**: 현재 규모와 요구사항을 고려해서 결정한다. 트래픽이 낮은 초기에는 성능 경고를 인지만 해두고 넘어갈 수 있다.
- **Info 약점**: 기록만 해두고 넘어간다.

보완 과정에서 새로운 의문이 생기면 design-challenger를 다시 실행할 수 있다.

### 4단계: 결정 문서화

`decision-documenter`를 실행한다.

기록할 대상:
- 기술 선택 (락 전략, 아키텍처, 프레임워크 등)
- design-challenger에서 발견된 약점과 보완 결정
- 의도적으로 미해결로 남긴 약점과 그 이유

좋은 결정 문서의 기준: "6개월 후 이 코드를 처음 보는 사람이, 왜 이렇게 했는지 이해할 수 있는가?"

### 5단계: 구현 진행

설계가 충분히 검토되고 결정이 문서화되면 구현으로 넘어간다. 이 시점에서 구현자(사람 또는 AI)는 다음을 갖추고 있다:

- 명확한 요구사항 (1단계)
- 알려진 위험과 대응 방안 (2-3단계)
- 각 결정의 근거 (4단계)

## 언제 이 워크플로우를 쓰는가

**적합한 경우:**
- 동시성, 분산 시스템, 결제 등 정합성이 중요한 도메인
- 요구사항이 모호하고 숨겨진 복잡성이 의심되는 경우
- 여러 기술 대안 중 선택이 필요한 경우
- 나중에 "왜 이렇게 했지?"가 문제될 수 있는 설계

**과잉인 경우:**
- 단순 CRUD, 설정 변경, 버그 수정
- 이미 검증된 패턴을 반복 적용하는 경우
- 프로토타입이나 실험적 구현

판단이 애매하면 2단계(design-challenger)만 빠르게 돌려보는 것을 권장한다 — 약점이 나오면 전체 워크플로우로, 안 나오면 바로 구현으로 넘어간다.
